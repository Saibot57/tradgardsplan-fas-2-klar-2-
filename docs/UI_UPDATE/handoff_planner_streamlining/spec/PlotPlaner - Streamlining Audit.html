PlotPlaner UI streamlining audit · v1
20 maj 2026 For Saibot57 / geometry-sandbox

Less chrome,
more garden.

A plan to declutter the planner — by moving most of today's top bar off the top bar, promoting the canvas to protagonist, and giving the gardener one obvious next move at every step.

Scope
Web app — toolbar, inspector, canvas interactions, time slider, empty state, scene management.
Philosophy
Bold IA rethink. Hide secondary tools. Use contextual UI. Keep nothing on screen that doesn't earn its place.
Audience
Returning hobbyists iterating on a known plot.
Constraint
In-product copy stays Swedish ("du"-form, sentence case, drafting-book voice).
Anchor
PlotPlaner design system — paper + ink, sage / soil / sun / sky accents, Montserrat + Cabin + JetBrains Mono.
TL;DR

One toolbar becomes four surfaces that each do one thing. The 14-control top bar becomes a 5-control top bar. Tools move to a left rail. Sun & time get their own bottom strip. Everything else becomes contextual — and stays out of the way until needed.

01 / Diagnosis

The top bar is doing nine jobs at once.

Every action in the planner today lives on a single 44 px horizontal strip — add & remove, undo, file I/O, selected-rect controls, the time slider, sun readout, plot boundary, grid snap, north rotation, bed depth, area totals, collision status. It's a deep-tool toolbar pretending to be a header.

The bar overflows horizontally on anything narrower than ~2400 px. The codebase already acknowledges this with overflow-x: auto — the toolbar is hiding from itself. Eight separate concerns sit side by side as if they were equal, separated only by hairline dividers. There is no hierarchy: "Spara JSON" and the sun-altitude readout get the same visual weight as "Lägg till bädd", which is the only action a first-time visitor needs to find.

1

Title squeezed into a toolbar. The wordmark and "geometry sandbox" label live where Add Bed should be the loudest thing on screen.

2

"+ Rektangel" isn't a primary action. It looks like every other secondary button. The single most-used verb of the app has no visual claim.

3

File I/O sits in the top bar always. "Spara JSON" / "Ladda JSON" are once-a-session actions, not at-hand actions. They take the same space as undo.

4

Per-selection controls leak into the bar. Rotate and wall-height appear and disappear in the top bar depending on selection — they belong to the bed, not to the chrome.

5

The sun readout is dev output. "Sol: alt 41.2°, az 187.5°" reads like a console log. Useful for debugging the math; opaque to a gardener.

6

Three unrelated settings in one section. "Skapa tomt", grid snap, and north rotation share a group with no visible reason. North rotation is set once per plot, ever.

7

Bed depth is a global slider hidden in plain sight. It changes the soil-volume of every bed at once, but lives between a measurement label and a Greek sigma.

8

Status messages don't earn the toolbar. Σ totals and the collision count are read-only — they belong in a quieter status row, not crammed into the action surface.

"A toolbar should answer the question 'what can I do?'. PlotPlaner's toolbar answers 'what does this app contain?'. Those are very different questions."

— observation, this audit
02 / Principles

Five rules for the rebuild.

Before redrawing anything, here's what every decision in the rest of this document is measured against. Each is in service of the design system's stated stance: a drafting table for the garden — paper, ink, pencil, honest measurement.

P1

One surface, one job.

The top bar is for app-level chrome. The rail is for tools. The bottom strip is for time. The inspector is for the selected object. No surface does more than one thing.

P2

Contextual over persistent.

Per-object controls (rotate, wall, delete) live on the object — as a floating toolbar over the selection — not on the chrome. The chrome doesn't change when you click a bed.

P3

Verbs first, settings second.

Primary verbs (add bed, draw wall, define plot) are visually loud and shortcut-accessible. Settings (grid step, north rotation, bed depth) hide behind a quiet menu.

P4

The canvas is the protagonist.

Every chrome decision asks: does this make the canvas easier to look at? If a control can be smaller, hidden behind a hover, or moved off-canvas, it should be.

P5

Numbers should be readable, not raw.

"Sol: alt 41.2°, az 187.5°" becomes "Sol 41° över horisonten · sydsydväst". Raw degrees stay available — in tooltips and a dev mode — but never lead.

P6

Keyboard is first-class.

This is a desktop tool used by returning hobbyists. Every primary verb gets a one-letter shortcut. The shortcut is shown on the icon, not hidden in a tooltip.

04 / The top bar

From 14 controls to 5.

The new top bar exists to answer one question: which plot am I in, and what do I want to do with it as a whole? Tools have left. Settings have left. Per-selection controls have left. What stays is identity, the scene name, and the rare actions that operate on the entire scene.

What's left, and what isn't

The wordmark stops being a label and becomes a brand mark with a small plot-rectangle glyph beside it. Beside the wordmark, the scene title takes the position that used to belong to a debugging subtitle ("geometry sandbox"). The gardener's plot now has a name; clicking the chevron opens the scene menu (see §10). A small mono timestamp tells them, quietly, that autosave just ran.

On the right: a help affordance, the theme toggle (paper / evening), and one button — Dela — which is the new home for save/export. Three icons that don't shout, plus one verb. That's it.

Everything else has moved. Lägg till bädd and Ta bort are now tools on the left rail; Ångra / Gör om are keyboard-only with a small ⌘Z hint under the scene name; Spara / Ladda JSON are inside the scene menu; Skapa tomt is now the empty-state hero (§09) and also a left-rail tool; per-selection controls are floating handles on the canvas (§06); grid snap, north rotation, bed depth, shadow toggle are inside an inline Inställningar popover that lives next to the scene name and is closed by default.

06 / Canvas & contextual UI

Per-selection controls move onto the bed.

Today, rotating a bed means looking up — to the top bar — and clicking ↺ -15° next to text reading Vald: rect-2. The mouse leaves the work to operate the work. The fix is the pattern every modern canvas app uses: a small floating toolbar that follows the selection.

1

Floating selection toolbar. Appears 8 px above the selected rectangle. Carries the per-bed verbs that used to live in the top bar — rotate ±15°, convert to wall, duplicate, delete — plus an at-a-glance label ("Bädd · 2,00 × 1,00 m · 15°"). Disappears on deselect.

4

The label echoes the inspector. For the gardener actively dragging, the small label above the bed says everything the right panel says. The inspector is for sitting and reading; the floating toolbar is for working.

Snapping & modifier keys

  • Default snap is on. Returning hobbyists move beds in whole-centimetre increments far more than free-floating ones. The codebase ships with snapToGrid: false — we flip that.
  • Hold Alt to suspend snap mid-drag, the convention from every CAD tool. The grid checkbox in the top bar disappears.
  • Hold Shift while rotating for free rotation; release for 15° detents. (Today, only 15° detents exist.)
  • Hold Shift while resizing to keep aspect ratio.
  • Arrow keys nudge the selected bed by one grid step (or one mm with Shift).

Three deliberate changes

1. Sun hours becomes the hero. A 48 px mono number with a small "h" sets the visual hierarchy of the panel. The single most decision-relevant value gets the most ink. A one-line plain-language gloss ("bra för tomat och paprika" / "lite för sallad — kanske rödbeta") goes underneath. Behind that line sits a small lookup keyed to a few common Nordic crops.

2. Field rows are now editable in place. The current panel is read-only. The new Geometri section accepts direct numeric input — type 2500 into Mått and the bed grows. Mirrored from the floating toolbar; either surface works. Editing in the panel is for typed precision; dragging is for spatial feel.

3. The empty state means something. Today: "Markera en bädd för att se detaljer." Proposed: the panel turns into a Scene panel — list of every bed (clickable rows, with sun-hours), total area, total soil volume, plot dimensions. The gardener gets a sense of the whole plot when nothing is selected. (See §10 for what this looks like as a full panel.)

The aggregate sun-hours number in the inspector is a separate calculation across the whole day — the inspector caption already says so, and we keep that note. They don't share state, and the visual separation between the right panel's hero number and the bottom bar's scrubber reinforces that.

The chrome never explains what's already obvious from the drawing.

10 / Scene management & save/load

Files, not "Spara JSON".

Today, saving means clicking Spara JSON, the browser downloads scene.json, and the gardener has to remember where they put it. Loading means clicking Ladda JSON, finding the file again, and accepting that the app forgot everything. This is fine for a debugging sandbox; it is wrong for the only file your gardener cares about.

1

The scene is named, in the top bar. "Norra tomten · sparad 14:32" is permanently visible. Clicking the chevron opens the scene menu. Click the name to rename in place.

2

Local-first autosave. Every change writes to localStorage on a 600 ms debounce. "Spara JSON" becomes "Exportera som JSON" — a backup action, not a primary action.

3

4

Honest about storage. A small mono note in the corner reminds the gardener their work lives in this browser. Exporting JSON is offered as a backup, not as the save model.

Why this matters more than it looks

For a returning hobbyist, the single biggest UX failure of today's app is that scene.json is the system of record. They open the planner three weeks later, see a blank canvas, and have to find a file in their Downloads folder. By making the browser remember, and treating JSON export as a backup convenience, the app stops being a sandbox and starts being a tool you trust.

13 / Open questions & risks

Where this plan needs decisions, not designs.

A bold redesign of a single-developer project is a budget decision as much as a design decision. These are the choices I'd rather flag than silently make on your behalf.

1. Is the left rail worth the floor space?

A 56 px rail costs roughly 4 % of canvas width on a 1440 px screen. The win is that adding beds becomes a one-key action (B) and the toolbar can collapse dramatically. If you'd rather optimise for canvas-first feel, the rail can become a small floating tool-popover anchored top-left, opened with ⌘K. I recommend the visible rail — returning hobbyists discover tools they didn't know existed by glancing at it — but the floating variant is a defensible alternative if you want maximum canvas.

2. Is autosave a database call or pure local?

The whole audit assumes localStorage as the storage model. That's a one-day implementation. If you have any intent to add accounts, sync, sharing, that "Dela" button in the top bar becomes a real share action, scene names become server-owned, and we need an auth boundary. The redesign works either way — but the copy ("Allt sparas i din webbläsare") only stays true under the local-only model.

3. Should "vägg" remain a property of "bädd", or become a separate object?

The data model today flattens both into Rect { wallHeight: number }. The new UI treats them as different tools (B vs W), different colours (sage vs warm grey), and different verbs. That works visually with the current model, but at some point a wall might need thickness or opacity that a bed doesn't. Worth a model conversation before any of this ships.

4. How aggressive should we be about Swedish-first copy?

I've assumed the design system's stance: "in-product copy is Swedish". That means "Lägg till bädd" not "Add bed", "rita" not "draw", and so on. Where the codebase carries English nouns ("wallHeight"), I'd keep the English in code and translate at the UI boundary. If you want bilingual UI (toggle in settings), that's an extra layer of polish but easy to add on the labels in this audit.

5. What's the smallest viable first slice?

If we ship this in one go, it's two weeks of work. If we ship it incrementally, here's the order I'd recommend, each shippable on its own:

  1. Visual refresh first. Apply the design system's paper-light tokens to the existing layout. Same controls, just calmer. (~1 day.)
  2. Bottom time bar. Promote the slider out of the top bar. Big perceived win for very little code. (~1 day.)
  3. Floating selection toolbar. Remove per-selection controls from the top bar. (~1 day.)
  4. Left rail. Move Add Bed and Wall to a vertical tool palette. (~2 days.)
  5. Inspector rebuild. Sun-hours hero, editable rows, Scene-panel empty state. (~2 days.)
  6. Local autosave + scene menu. The biggest UX impact for returning users. (~3 days.)
  7. Empty state + onboarding. Once everything else is in place. (~1 day.)

Steps 1–3 alone would already reduce the top bar from 14 controls to about 6, on a budget of one weekend.

"Decluttering isn't subtraction. It's putting each thing where the work actually happens — and trusting the gardener to find it there."
